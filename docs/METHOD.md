# The method — what this template encodes

For a human who wants to understand the model before launching a wiki with it. The
contract itself is [CHARTE.md](../CHARTE.md); the step-by-step install is
[SETUP.md](SETUP.md); the agent-side procedure is
[AGENT-PROTOCOL.md](AGENT-PROTOCOL.md).

## 1. What this is — and is not

An **agent-maintained knowledge wiki**: consolidated declarative knowledge, organized
by subject into OKF bundles, in plain Markdown, versioned with Git. Agents read,
write and maintain it; a human owner curates sources and arbitrates. It is *not* a
capture surface, not an action system, not a personal memory, not a configuration
repository — those live elsewhere, and the routing filter enforces the distinction.

Positioning that makes the system work: **conversational memory** keeps
personal-contextual observations; the **owner's action system** keeps operational
material; the **wiki** keeps consolidated, source-grounded, publishable knowledge.
The wiki does not capture (an inbox does that), does not execute (no tasks), and
agents never write into the other two systems during a wiki operation.

## 2. The model in five sentences

1. Knowledge lives in **bundles** — one directory per knowledge domain, with five
   typed sub-directories (concepts, entities, syntheses, references, immutable raw).
2. **Agents write, the owner arbitrates**: every structural decision (new bundle, new
   synthesis, charter change) requires an explicit "yes" — silence means no.
3. **Two write channels, one lint**: local agents commit through `tools/commit.sh`
   (lock → regenerate indexes → lint → commit → rebase-push); remote agents open pull
   requests and never touch `main`.
4. **Everything is deemed publishable**: impersonal writing, public URLs only,
   anonymization at writing time, enforced by a three-tier lint (local with a private
   denylist / CI with generic patterns / weekly semantic pass).
5. **Provenance is triple-tracked**: frontmatter (`generated`, `verified`, `sources`)
   for business provenance, commit trailers (`Acting-Agent:`) for technical
   provenance, per-bundle `log.md` for the chronicle — all greppable, which is what
   the weekly metrics block is made of.

## 3. Design decisions (the "why")

These are the decision records behind the template. They were settled in production,
not on a whiteboard.

| # | Decision | Why |
|---|---|---|
| D1 | **One Git repository** (local source of truth, private remote for backup + remote agents) | Zero cost, free PR/blame/history from the forge, and OKF's own stance that bundles live in git |
| D2 | **OKF v0.2 strict** for every bundle page | Follow an existing spec rather than reinvent; community tooling; trivial export/import |
| D3 | **Multi-bundle layout** — `bundles/<name>/` is one wiki | Scales by domain; each bundle stays small enough for index-first search |
| D4 | **`raw/` immutable per bundle**, sources converted to markdown at ingestion, no binaries | The anti-model-collapse layer: the wiki's claims stay auditable against untouched sources |
| D5 | **Indexes generated by script, never hand-edited** | Eliminates index drift and the hottest merge-conflict spot in one move |
| D6 | **Lint in tiers** — structural (pre-commit + CI) and semantic (weekly agent pass) | Experience shows either one alone fails: structure without semantics rots, semantics without tooling never runs |
| D7 | **Search by tiers** — index + ripgrep, then BM25-only (`qmd search`) past ~100 pages per bundle | Index-first is sufficient and infrastructure-free at moderate scale; hybrid LLM search measured at minutes per query on CPU-only hosts |
| D8 | **A single charter at the root** + thin on-ramps (`AGENTS.md`/`CLAUDE.md`); agent skills are only on-ramps | One contract every agent reads; convention changes happen in the charter first, never in scattered skills |
| D9 | **Remote access through the forge** (read directly, write by PR); a self-hosted MCP server is a later, read-mostly option | No new network surface; PR gating joins the owner-validation requirement |
| D10 | **No bundle without explicit owner validation** — formal proposal process, locked by the lint (inventory) | Hard owner requirement; the inventory table is the machine-checked registry |
| D11 | **Attributed commits** — generic author + `Acting-Agent:` trailer; frontmatter = business provenance, commit = technical | "If someone breaks the wiki, their name is on it" — with actor conventions that stay publishable |
| D12 | **Human navigation** — tree + hierarchical indexes, opens as an Obsidian vault | Answers the "flat dumps are unnavigable" critique |
| D13 | **Publishability by default** — everything in a bundle is deemed publishable as-is; anonymization at writing; automated scan + private denylist outside the repository | Publishing must never require restructuring; the denylist stays out precisely because it is the one thing that must not leak |
| D14 | **Declared audience** (template 2.0) — "releasable" targets the audience declared in the charter header (public by default, narrower allowed); secrets and personal data stay absolute at any audience | Professional deployments need the method without the public-by-default assumption — one parameter, zero new machinery |
| D15 | **Engineering profile as charter §13, native** — Decision/Constraint types, `code_refs`/`applies_to`/`source_file`+`conversion` fields, code-mapping and document-base methodologies; removable as one commit (Annex A) | The contract stays single (D8); a profile directory would fragment authority, and grandfathering keeps removal migration-free |
| D16 | **Two new types only** — no `Component` (a Tool/Service/Concept + `applies_to` covers it), no `Interface` (a Concept + `code_refs`; a type would push toward duplicating signatures), no `Test` (Playbook exists) | Every type is a routing decision an agent must make per page; minimal vocabularies route faster than complete ones |
| D17 | **Binaries: hash + out-of-repo reference** — `source_file.sha256` as the document dedup key, conversion declared, git-lfs an owner exception; documents split per chapter, same-date sharing tolerated by the lint | Keeps the repository text-only (D4) without losing provenance; the binary lives where the project already keeps it |
| D18 | **The pinned commit IS the version** — full 40-hex sha in `code_refs`, `stale_after` mandatory alongside; no version field | A second version field would drift from the sha; the coupling makes re-verification automatic through the freshness loop |
| D19 | **Codebases and document funds are attacked by methodology, not ingestion** — orient → read history → mine tests → filter → pin (§13.7); inventory → per-chapter filter → prioritize by pain (§13.8) | Agents fail at "read everything"; the wiki captures the non-obvious, the repository remains the source of record |

Two decisions that cut across everything: **`merge=union` on `log.md`** (`.gitattributes`)
makes concurrent append by parallel agents safe by construction, and the commit lock
uses **close-on-exec** so forked daemons cannot inherit it — both were paid for in
incidents, and both are encoded in the shipped tooling.

## 4. Ordered bootstrap

The order matters; each step's exit is the next step's prerequisite.

1. **Scaffold** — repository, tree, `.gitattributes`, git hooks (the classic miss:
   git never copies hooks on clone — `init.sh` wires `core.hooksPath`), CI workflow,
   charter skeleton with empty inventory markers.
2. **Tooling** — `gen-index.py`, `lint.py` (generic publishability patterns; the
   private denylist initializes *empty, outside the repository*), `commit.sh`.
3. **Empty-state validation** — run the lint on the empty structure; it must exit
   clean. Then run a **voluntary leak test**: inject a known private marker into a
   scratch page and verify the lint *rejects* it (recipe in
   [SETUP.md](SETUP.md) B8). A gate that has never been seen to close is not a gate.
4. **Owner review** of the charter and the residual decisions (language, thresholds,
   where the remote lives).
5. **First bundle** — by the book: a proposal is filed, the owner says yes,
   `new-bundle.sh` creates the skeleton and the inventory row, the relocation sweep
   runs. The first real content proves the pipeline end to end.
6. **Agent on-ramps** — point every agent at the repository (their skills only
   on-ramp to the charter); give remote agents the PR channel.
7. **Automation, incrementally** — weekly semantic lint, then (optionally) routine
   PR automerge, then (optionally) a GitHub App for API-only agents. Each layer is
   independent; the wiki works without any of them.

## 5. Governance

| Role | Does | Never does |
|---|---|---|
| Owner | Validates bundles and syntheses, grants `verified human:`, arbitrates contradictions, curates sources, evolves the charter | — |
| Local agent | Reads wiki-first, writes via `commit.sh`, files proposals, runs the lint | Creates bundles/syntheses unasked; touches structural files |
| Remote agent | Reads, writes by branch + PR | Writes `main`, edits indexes |
| Maintenance process (`process:lint-weekly`) | Mechanical fixes, reports, metrics | Creates/merges/synthesizes anything |

**Silence means no** — the default answer to any pending validation. Proposals live
in `proposals/`, then move to `validated/` or `refused/` when arbitrated; the refused
ones keep their rationale (they are the institutional memory of the noes).

**The relocation sweep** (charter §10.5) deserves emphasis because it is the step
everyone skips: a new bundle created without re-judging every `routing_review` page
and everything its scope could claim leaves the wiki in the exact state that
motivated the bundle's creation.

## 6. The maintenance loop

The weekly semantic lint (charter §8.F) is the heartbeat. Checklist: passed
`stale_after` and freshness lags → re-verify or deprecate; dormant drafts > 30 days;
behind syntheses → reread against covered pages; `routing_review` pages → re-judge
against the inventory, open a proposal when ≥ 3 pages point at the same candidate;
`contested` pages → resolve by rotation; rotating review of one tag cluster
(rotate weekly and log which — coverage degrades silently otherwise); duplicates →
propose merges, never auto-merge; orphan pages; unclean `git status`. The report
ends with a **metrics block** grepped from the `log.md`s: actions per bundle, the
week's `Query-miss` entries, pages per bundle against the ~100 threshold, pages
never cited in any log entry.

## 7. Tunables

Every threshold, with where it lives:

| Threshold | Default | Where |
|---|---|---|
| Pages per bundle before search tier-up | ~100 | charter §11, `PAGES_PER_BUNDLE_THRESHOLD` in `metrics.py` (env `WIKI_PAGES_THRESHOLD`) |
| Bundle creation potential | ≥ ~10 pages | charter §10 |
| Bundle split flag | ≥ threshold, two weeks running | charter §10.6, `metrics.py` |
| Synthesis theme threshold | ≥ 5 pages | charter §6.5, `SYNTH_THEME_MIN` in `lint.py` |
| Synthesis adrift warning | ≥ 3 uncovered pages | `SYNTH_COVERAGE_WARN` in `lint.py` |
| Tag "too broad to be a theme" | 60% of a bundle's pages | `SYNTH_TAG_TOO_BROAD` in `lint.py` |
| Freshness lag | > 90 days behind freshest source | `FRESHNESS_LAG_DAYS` in `lint.py` |
| Long-page split candidate | > 200 lines | `LONG_PAGE_LINES` in `lint.py` |
| Dormant draft | > 30 days | charter §8.F |
| Contested escalation | > 60 days | charter §8.F, `CONTESTED_ESCALATE_DAYS` in `metrics.py` |
| Document auto chapter-split | > 1500 lines | `CHAPTER_SPLIT_LINES` in `ingest-doc.sh` |
| Durability test | true in 6 months | charter §7.1 |
| Default language | English (per-topic exceptions) | charter §1 |
| Declared audience | public | charter header, §2 |
| Denylist location | `~/.config/wiki-lint/denylist.txt` or `$WIKI_DENYLIST` | `lint.py` |

## 8. Evolving the charter — and porting upstream changes

- Charter changes happen **in the charter first**, in a dedicated commit, and are
  always reported to the owner. When §5 (frontmatter) changes, `schemas/`,
  `templates/` and the lint's checks change **in the same commit** (the
  triple-lock rule — a schema that drifts from the lint is worse than none).
- This template is version **2.0**, derived from production charter v2.1 and
  template 1.0. The 2.0 additions: declared audience (D14), the engineering
  profile §13 with its two types and four fields (D15–D17), bundle-split and
  contested-resolution procedures, `tools/metrics.py`, `tools/ingest-doc.sh`,
  the versioned test suite, and the documentation set (ARCHITECTURE,
  IMPLEMENTATION-GUIDE, the MCP guide). If you derived your wiki from an
  earlier version, upstream improvements flow the same way: read the diff,
  port section by section, and let your own inventory and thresholds decide
  what applies. Your charter is yours once you have personalized it — keep the
  lineage note (template version in the header) so future-you knows what
  "upstream" means.
